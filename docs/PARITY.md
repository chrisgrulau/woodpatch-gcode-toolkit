# Parity ledger: the core against upstream

Generated by `node tools/parity.mjs` from `tools/data/parity-ledger.json`; CI checks it (ADR-0025). Do not edit by hand.

Every fixture runs through upstream's own parser (regenerated, and verified against its golden) and through the core (LinuxCNC 2.9 dialect). Their paths are compared line by line: each move's kind, end point (to 0.1 µm) and feed, and for arcs the centre and the signed sweep (to 1 µrad). A line where they differ must be explained by a rule below, which names the upstream defect or the decision behind it. **Everything not listed is identical.**

## Rules

| Rule | Ref | Lines | Why the core differs |
| --- | --- | ---: | --- |
| R1 | R1 | 1 | Upstream's expression evaluator recursed until the stack overflowed (RangeError) and drew nothing for the whole file. The core evaluates expressions with LinuxCNC's rules (ADR-0018). |
| R2 impossible R arc | R2 | 1 | The radius can't reach the end point. Upstream computed a NaN centre, drew nothing, said nothing, and carried on from the arc's end. The core refuses the line, and the tool stays where it was (ADR-0022). |
| R2 R-format full circle | R2 | 1 | An R-format arc ending where it starts has no defined centre. Upstream drew a NaN arc silently; the core refuses it, as LinuxCNC's arc_data_r does (ADR-0022). |
| R3 full circle | R3 | 1 | `G2 I-5` with no axis words is a valid full circle. Upstream dropped it silently; the core draws it (ADR-0022). |
| R4 canned cycle expanded | R4 | 4 | Upstream reported the cycle, then drew a rapid plunge to depth. The core draws the real cycle: rapid to R, feed to Z, retract (ADR-0020). |
| R4 canned cycle repeated | R4 | 1 | A later hole of the same cycle: upstream rapids across at depth, and the core drills it (ADR-0020). |
| G84-G89 not implemented | R4 | 6 | G84–G89 are recognised and refused as not implemented yet: a stated gap, not a guess. LinuxCNC has them; the Masso doesn't. Upstream drew them as rapid plunges (ADR-0020). |
| R5 G91 with a work offset | R5 | 3 | Upstream re-added the work offset on every incremental move (101, 202, 303). The core applies it once, giving 1, 2, 3 from machine X0 (ADR-0019). |
| R6 exponent | R6 | 1 | `X1e3` is X1 followed by an E word. Upstream moved to X1, taking E as an axis. E isn't a word here, so the line doesn't run, and the diagnostic explains the exponent reading. |
| R7 rotary words | R7 | 1 | Upstream failed the whole line on A/B/C and lost the X move. The core tracks A/B/C and runs the line. |
| R7 unclosed comment | R7, N10 | 1 | Line 2's `(` never closes, so the line isn't run, as LinuxCNC refuses it, and its F100 never takes effect. Line 3 then has no feed, so the core refuses it. Upstream fed it at a silent 200 mm/min (N10). |
| R8 lines after program end | R8, N12 | 2 | M2/M30 end the program. Upstream ignored M codes and drew the moves after them. |
| R8 arc-distance modes | R8 | 2 | Upstream threw on G90.1 and drew nothing for the file. The core implements G90.1/G91.1 (ADR-0019). |
| R8 checksum | R8 | 1 | Upstream failed the line on its `*nn` checksum and lost the move. The core ignores the checksum, with a warning, and runs the line. |
| R8 O-word subroutine | R8 | 1 | Upstream couldn't read O-words and drew nothing. The core runs the subroutine (ADR-0021). |
| N6 G28 home | R8, N6 | 1 | G28 goes to its stored home, which is unset, so the machine origin. That's where the tool already is, so the move is zero-length. Upstream reported G28 and drew nothing. |
| R8 inverse time (G93) | R8 | 1 | Under G93, F2 means the move takes half a minute. Upstream read it as 2 mm/min; the core records an inverse-time feed. |
| N4 bare-CR line endings | N4 | 3 | The file uses CR line endings. Upstream read the whole file as one line, so the last word won. The core reads three lines and draws each move. |
| N3 repeated words | N3 | 1 | Many X words on one line. Upstream used the last one; RS274 makes a repeated word an error, so the line doesn't run. |
| R9 zero-length moves kept | R9 | 64 | A move to where the tool already is. Upstream dropped moves under 10 µm without advancing. The core keeps every move, so paths, line mapping and events stay complete; the estimator ignores their length. Every such line in the upstream samples is this. |
